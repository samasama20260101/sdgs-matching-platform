# 明日もsamasama | SDGs MATCH サービス仕様書

最終更新: 2026-06-05

## 1. 本書の位置づけ

本書は、明日もsamasama | SDGs MATCH のサービス全体像、利用者別機能、主要な業務ルール、運用上の注意点をまとめた仕様書です。

開発メンバー、テスト担当者、運営メンバー、協力団体への説明に使うことを想定しています。

法務上の利用規約・プライバシーポリシーそのものではありません。契約・個人情報保護・免責などの正式文書は、公開ページの利用規約・プライバシーポリシーを正本とします。

## 2. サービス概要

| 項目 | 内容 |
|---|---|
| サービス名 | 明日もsamasama | SDGs MATCH |
| 運営 | 合同会社ｓａｍａｓａｍａ |
| 目的 | 社会的困難を抱えるSOSユーザーと、NPO・行政・企業などのサポーターをつなぐ |
| 主な対象 | 支援を求める個人、支援団体、運営管理者 |
| 対象地域 | 日本・インドネシアを想定。初期は日本向け運用を中心とする |
| 未成年定義 | 18歳未満 |
| 技術基盤 | Next.js / Supabase / Vercel / Google Gemini AI |

明日もsamasamaは、相談者がSDGsを意識しなくても、困りごとを入力できる場所です。

SDGsはサービス側・サポーター側の整理や発信の言語として使い、SOSユーザーには「助けてほしい」「相談したい」という自然な言葉で使ってもらう設計です。

## 3. サービス思想

### 3.1 SOSユーザーにSDGsを背負わせない

SOSユーザーは、自分の困りごとがどのSDGsに該当するかを理解している必要はありません。

相談内容の分類や整理は、サービス側が裏側で行います。

### 3.2 行政・NPO・企業が混在する意味

行政は制度の枠で支援します。

NPOや地域団体は、その枠からこぼれる困りごとを拾える場合があります。

企業は資源、専門性、地域接点を持っています。

この3者が混在することで、相談者にとって複数の支援可能性を持つ場所にします。

### 3.3 最後のセーフティネット

マッチングがうまくいかない場合でも、運営へつながる導線を残します。

「誰にも届かなかった」で終わらせないことを重要なサービス要件とします。

## 8. SOSユーザー機能

### 8.1 ダッシュボード

SOSユーザーは `/sos/dashboard` で自分の相談状況を確認します。

主な表示:

- 表示名でのあいさつ
- 地域未設定時のプロフィール設定案内
- 自分の相談カード
- 進行中・完了済みの相談状況

### 8.2 プロフィール編集

`/profile` でSOSプロフィールを編集します。

UI上は、以下のように個人情報と支援提案用情報を分けます。

| 区分 | 主な項目 | 表示方針 |
|---|---|---|
| 非公開の連絡先 | 氏名、メールアドレス、電話番号 | サポーター公開画面には出さない |
| サポーターに表示される情報 | ニックネーム | 支援者とのやり取りで表示 |
| 支援提案に使う地域 | 地域コード、地域名 | マッチング・提案・管理追跡に使用 |
| 詳細住所 | 任意の住所情報 | 原則非公開 |

### 8.3 相談投稿

SOSユーザーは `/sos/hearing` から相談を投稿します。

Q1〜Q5は必須情報です。

自由記述の「いま何が起きていますか？」も必須です。

投稿後、AI分析やSDGs分類を行い、相談結果・相談詳細へ進みます。

主なAPI:

| API | 役割 |
|---|---|
| `/api/sos/cases` | 相談作成・取得 |
| `/api/sos/cases/[id]` | 相談詳細取得 |
| `/api/classify-sdgs` | SDGs分類 |
| `/api/gemini/analyze` | 相談内容分析 |

### 8.4 支援申し出の確認

サポーターから申し出がある場合、SOSユーザーは相談詳細画面で確認します。

SOSユーザーは申し出を承認または辞退できます。

申し出は団体名中心で表示し、担当者個人情報を前面に出しません。

### 8.5 メッセージ

マッチ後、SOSユーザーはサポーターとメッセージをやり取りできます。

サポーター内部メモはSOSユーザーには表示しません。

主なAPI:

| API | 役割 |
|---|---|
| `/api/messages` | メッセージ取得・送信 |
| `/api/sos/offers/[id]` | SOS側の申し出操作 |

## 9. サポーター機能

### 9.1 団体と担当者の考え方

サポーターは団体として支援します。

ただしログインや操作は、団体に所属する担当者個人アカウントで行います。

主なDB上の考え方:

| 要素 | 役割 |
|---|---|
| `organizations` | 団体情報の正本 |
| `organization_memberships` | 個人ユーザーと団体の所属 |
| `users` | ログインする個人 |

所属ロール:

| 所属ロール | 説明 |
|---|---|
| OWNER | 団体情報、公開プロフィール、メンバー管理を行える責任者 |
| ADMIN | 将来の管理権限拡張候補 |
| MEMBER | 担当者個人情報を管理し、案件対応に参加する |

最後のOWNERは停止・解除・降格できないように保護します。

1人のユーザーが同時に複数団体へ所属することは、現時点ではDB制約で禁止します。

### 9.2 サポーターダッシュボード

サポーターは `/supporter/dashboard` で対応可能な相談案件を確認します。

主な表示:

- 対応可能な相談案件一覧
- 相談概要
- SDGs分類
- 地域情報
- 自団体の申し出状況

### 9.3 サポータープロフィール編集

`/profile` では、担当者個人情報と団体情報をUI上で分けます。

| 区分 | 主な項目 | 編集権限 |
|---|---|---|
| あなたの担当者情報 | 担当者名、表示名、メール、個人電話、部署、外線、内線 | 本人 |
| 団体情報 | 団体名、団体代表電話、団体所在地、活動地域 | OWNER |
| 公開プロフィール | 自己紹介文、公式サイト、外部リンク | OWNER |

団体代表電話と担当者個人電話は別項目です。

団体所在地と担当者個人住所も混在させません。

### 9.4 メンバー管理

OWNERは `/supporter/members` で団体メンバーを管理します。

主な操作:

- メンバー一覧表示
- 新規メンバー追加
- 担当者情報の確認・編集
- MEMBER停止
- MEMBER復帰
- 最後のOWNER保護

第一弾では、団体メンバーの移籍・再所属・所属解除は扱いません。
そのため `/supporter/members` の「登録済みアカウントを所属に追加」導線と所属解除ボタンは表示せず、APIでも `registration_type = existing` と `status = LEFT` への変更を拒否します。
一時的に利用を止める場合は「停止」を使います。

団体内のメンバー停止は `organization_memberships.status = SUSPENDED` で管理します。
`users.is_suspended` と Supabase Auth ban は、管理者による全体アカウント停止専用です。
そのため、団体OWNERによる復帰・再所属操作では管理者停止を解除しません。

主なAPI:

| API | 役割 |
|---|---|
| `/api/supporter/members` | メンバー一覧・新規追加（登録済みアカウント追加は第一弾では無効） |
| `/api/supporter/members/[membershipId]` | メンバー更新・停止・復帰（所属解除は第一弾では無効） |

### 9.5 案件確認・申し出

サポーターは案件詳細 `/supporter/case/[id]` を確認し、支援申し出を作成できます。

同じ団体から同一案件へ重複申し出はできません。

申し出後、SOS側には団体名として表示します。

主なAPI:

| API | 役割 |
|---|---|
| `/api/supporter/cases/[id]` | サポーター向け案件詳細 |
| `/api/supporter/cases/[id]/offer` | 支援申し出作成 |
| `/api/supporter/offers/[id]` | サポーター側の申し出操作 |

### 9.6 チャット・内部メモ

サポーターはSOSとのメッセージとは別に、内部メモを使えます。

内部メモはSOSユーザーには表示しません。

想定される内部メモ範囲:

| 種別 | 説明 |
|---|---|
| 自団体のみ | 自団体メンバーだけが確認 |
| 担当サポーター間 | 案件に関わるサポーター間で確認 |

主なAPI:

| API | 役割 |
|---|---|
| `/api/supporter/cases/[id]/internal-notes` | 内部メモ作成・取得 |
| `/api/messages` | SOSとのメッセージ |

### 9.7 解決済み操作

承認順が主サポーターの団体は、案件を解決済みに進められます。

副サポーターは原則として解決操作を行いません。

主サポーター判定には、申し出の承認順 `accepted_order` を使います。

## 10. 管理者機能

### 10.1 管理者ログイン・ダッシュボード

管理者は `/admin/login` からログインし、`/admin/dashboard` で全体状況を確認します。

主な表示:

- SOSユーザー数
- サポーター数または団体数
- 相談件数
- ステータス別件数
- 問い合わせ
- 注目サポーター

### 10.2 SOSユーザー管理

管理者はSOSユーザーを検索・確認し、必要に応じて停止・復帰できます。

管理上は、ニックネームだけでなく、氏名、メール、地域コードも追跡できる必要があります。

ただし、公開画面やサポーター画面に非公開情報を不用意に表示しません。

### 10.3 サポーター・団体管理

管理者はサポーター団体と担当者を確認します。

主な操作:

- サポーター団体作成
- OWNER作成
- サポーター停止・復帰
- 注目サポーター設定
- 団体情報・担当者情報の追跡

### 10.4 相談管理

管理者は相談案件を一覧で確認し、問題発生時に追跡します。

相談には `CASE-00001` のような管理用表示IDを付与します。

廃止済みステータス `IN_PROGRESS` は使いません。

### 10.5 地域コード一覧

管理者は `/admin/regions` で地域コードを追跡します。

主な表示:

- 地域コード
- 地域名
- SOSユーザー数
- サポーター団体数
- 全国対応の団体数
- 未マッピングの地域コード

複数地域を持つサポーター団体は、地域ごとにカウントします。

### 10.6 管理者作成

管理者は必要に応じて別の管理者を作成できます。

初回パスワード変更が必要な場合は、変更フローへ誘導します。

## 11. 相談案件とステータス

### 11.1 ステータス遷移

```text
OPEN
  -> MATCHED
       -> RESOLVED
       -> CLOSED
       -> CANCELLED
```

| ステータス | 意味 | カウント |
|---|---|---|
| OPEN | 相談投稿済み。支援申し出またはマッチ前 | 未解決 |
| MATCHED | SOSが申し出を承認し、サポーターとつながった状態 | 進行中 |
| RESOLVED | 解決済み。実績カウント対象 | 対象 |
| CLOSED | 14日無活動などで終了。実績カウント対象外 | 対象外 |
| CANCELLED | 取消・中断 | 対象外 |

`IN_PROGRESS` は廃止済みです。

### 11.2 承認上限

1案件あたりの承認済みサポーター上限は、現在2団体です。

```typescript
MAX_SUPPORTERS_PER_CASE = 2
```

将来3団体へ変更する可能性があります。

### 14.3 退会とデータ保持方針（未実装）

退会機能は現時点では未実装です。
実装時は、SOSユーザーとサポーター団体メンバーでデータ保持方針を分けます。

退会は、次の3つを区別して扱います。

| 区分 | 意味 |
|---|---|
| 退会 | 利用者が今後ログイン・利用しない状態 |
| 個人情報の削除・匿名化 | 氏名、メールアドレス、電話番号、住所、生年月日など個人を特定し得る情報を削除または内部用値へ置換すること |
| 物理削除 | DBレコードそのものを削除すること |

原則として、案件、メッセージ、支援履歴、監査ログは参照整合性とトラブル対応のため物理削除しません。
必要な範囲で個人情報を削除・匿名化します。

#### アカウント状態と所属状態の用語整理

「団体に所属していない」と「サービスを退会した」は見た目が似ていますが、意味を分けます。

| 用語 | 意味 | 主なDB表現 | 復帰・再利用 |
|---|---|---|---|
| 所属なし | アカウントは有効だが、現在どの団体にも所属していない | `users` は有効、`organization_memberships` に `ACTIVE` がない | 団体追加・移籍・再所属が可能 |
| 所属解除 | 団体との所属関係が終了した | `organization_memberships.status = LEFT` | 将来対応。第一弾では新規に作成しない |
| 団体内停止 | 団体内で一時的に利用を止めている | `organization_memberships.status = SUSPENDED` | OWNER/ADMINの操作で復帰可能 |
| 管理者停止 | サービス全体でログイン・利用を止めている | `users.is_suspended = true`、将来は `users.account_status = SUSPENDED` | 管理者解除まで復帰不可 |
| 退会 | 本人がサービス利用を終了した | 将来は `users.account_status = WITHDRAWN` | 方針に従って再登録または再有効化 |

UI上の用語は次を基本にします。

| 表示語 | 使う場面 |
|---|---|
| 所属なし | 有効なアカウントだが団体所属がない場合 |
| 所属解除 | 将来、団体メンバー一覧で過去所属として扱う場合。第一弾では操作不可 |
| 停止 | 管理者または団体管理者が一時的に利用を止める場合 |
| 退会 | 本人がサービス利用を終了する場合 |

初期実装では `users.account_status` は未導入です。
ただし、将来的には `users.is_suspended` だけで管理者停止・本人退会・所属なしを混ぜないよう、`account_status` の導入を検討します。

#### SOSユーザーの退会

SOSユーザーは、退会と同時に個人情報を削除・匿名化する方針です。
初期実装では保留期間を設けず、退会処理を軽く明確にします。

| 時点 | 方針 |
|---|---|
| 退会直後 | ログイン不可にし、個人情報を削除・匿名化する |
| 退会後 | 同じメールアドレスで新規登録できる状態にする |

退会処理では、旧アカウントのメールアドレスをそのまま残しません。
`users.email` は内部用の退会済み値へ置換し、Supabase Auth側も削除またはsoft deleteして、同じメールアドレスで新しいSOSユーザーとして登録できるようにします。

例:

```text
users.email
→ withdrawn_<user_id>@deleted.local

users.real_name / display_name / phone / birth_date / gender / address系
→ null または退会済みユーザー相当の値
```

旧アカウントの相談履歴を新アカウントへ自動復元・自動紐付けしません。
同じメールアドレスで再登録した場合も、新規ユーザーとして扱います。

#### サポーター団体メンバーの退会

サポーター団体メンバーは、支援提供者・団体担当者として案件対応、メッセージ、解決報告、団体管理操作、監査ログに関与します。
そのため、退会してもメールアドレスを原則保持し、完全な新規登録で同じメールアドレスを再利用できない方針とします。

| 情報 | 退会後の方針 |
|---|---|
| `organization_memberships` | `status = LEFT` として所属解除履歴を保持 |
| `users.email` | 監査・本人識別・再所属判定のため保持 |
| Supabase Auth | ログイン不可にする。物理削除は原則避ける |
| 担当者名 | 履歴上必要な範囲で保持。公開表示では「退会済みメンバー」などに置換を検討 |
| 任意電話番号 | 監査上不要であれば削除またはマスクを検討 |
| messages / offers / audit_logs | 物理削除せず保持 |

同じメールアドレスで再度関わる場合は、将来的には新規登録ではなく、既存アカウントの復帰・再所属・移籍として扱います。
ただし第一弾では復帰・再所属・移籍のUI/APIは開放せず、必要になった時点で管理者確認を含む運用として設計します。
本人退会済み、管理者停止中、または別団体に `ACTIVE` / `SUSPENDED` 所属中の場合は、通常の復帰ではなく管理者確認を必要とします。

最後のOWNERは退会できません。
退会前に別のOWNERを追加または昇格させる必要があります。

#### 実装時の注意

退会機能を実装する時点で、公開中の利用規約・プライバシーポリシーも必ず見直します。
現在のプライバシーポリシー第12条は「退会と同時にSOSユーザーの個人情報を削除します」としており、SOSユーザー退会方針とは整合しています。
サポーター団体メンバーの退会保持方針を正式実装する場合は、必要に応じて公開文書にも追記します。

DBとしては、将来的に `users.account_status`、`users.withdrawn_at`、`users.personal_data_deleted_at` のような状態管理カラムを追加することを検討します。
`users.is_suspended` は管理者による全体アカウント停止専用にし、本人退会とは意味を混ぜない方針です。

## 15. メンテナンスモード

Production DB変更中は、メンテナンスモードで通常操作を止めます。

| 変数 | 役割 |
|---|---|
| `MAINTENANCE_MODE` | `true` のとき通常ページを `/maintenance` へ誘導 |
| `MAINTENANCE_BYPASS_TOKEN` | 運営確認用ブラウザだけ通常画面を確認するための一時トークン |

メンテナンスモードは強制ログアウトを行いません。

セッションを保持したまま、作業中だけ画面/API操作を止めます。

詳細は `docs/maintenance_mode.md` を参照します。

## 16. 自動処理

Vercel Cronで毎日JST午前2時に自動処理を行います。

| 処理 | 条件 | 結果 |
|---|---|---|
| 解決確定 | サポーター解決報告から14日経過 | `RESOLVED` |
| 無活動終了 | `MATCHED` のまま最終メッセージから14日無活動 | `CLOSED` |

エンドポイント:

```text
/api/cron/auto-close-cases
```

## 18. テスト観点

Stagingでのロール別テストは `docs/staging_role_function_test_spec.md` を正本とします。

最低限確認する視点:

- SOSが相談投稿できる
- サポーターが案件確認・申し出・メッセージ送信できる
- OWNERが団体情報・活動地域・メンバーを管理できる
- MEMBERがOWNER専用操作を実行できない
- 管理者がユーザー・団体・相談・地域コードを追跡できる
- 非公開情報が公開ページや別ロールに漏れない
- メンテナンスモードが意図どおり動く
