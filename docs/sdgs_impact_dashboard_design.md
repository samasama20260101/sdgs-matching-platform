## 0. 方針サマリ（2026-07-06 ユーザー指示を反映）

1. **カウントは公式のSDGs指標体系に沿って行う**: 17ゴール → 169ターゲット → 指標
   （国連指標は231〜248件と数え方が揺れる。本システムのIDは公式指標ID「1.3.1」形式に揃え、
   **定義文だけを個人向けに独自整備**する = AGENTS.md「個人向けGI」方式。
   これにより行政報告・助成金審査で公式フレームワークにそのまま対応づけられる）。
2. **UIは17ゴールが入口であり、それ自体が完結した画面**。
   興味がない人・ライトユーザーは17タイルを見て満足して終われる。
   詳しく見たい人だけがタイル→ターゲット→GI→案件一覧へドリルダウンする（段階的開示）。
3. GIは細かすぎるため一覧の主役にしない。**デフォルト表示は常にゴールレベル**。

## 1. データモデル（migration ドラフト）

AGENTS.md 機能4のドラフトを、バリアント（§3.4）と多言語（ラベルjsonb化）を織り込んで確定する。

```sql
-- ─── ターゲットマスタ（169件・表示用） ──────────────────────
CREATE TABLE sdg_targets (
  id          text PRIMARY KEY,          -- '1.3'（公式ターゲットID）
  goal_id     integer NOT NULL CHECK (goal_id BETWEEN 1 AND 17),
  labels      jsonb NOT NULL,            -- {"ja": "社会保護制度の実施", ...} 当面jaのみ
  sort_order  integer NOT NULL DEFAULT 0
);

-- ─── 個人向けGI定義マスタ ───────────────────────────────────
CREATE TABLE sdg_indicators (
  id                 text PRIMARY KEY,   -- '1.3.1'（公式指標ID）
  goal_id            integer NOT NULL CHECK (goal_id BETWEEN 1 AND 17),
  target_id          text NOT NULL REFERENCES sdg_targets(id),
  labels             jsonb NOT NULL,     -- {"ja": "生活保護など公的支援につながった"}
  definition_ja      text NOT NULL,      -- AI②のプロンプト入力（個人向け定義文・日本語のみ）
  owner_variant_code text NULL,          -- NULL=共通GI / 値=版独自指標（バリアント§3.4）
  is_active          boolean NOT NULL DEFAULT true,
  sort_order         integer NOT NULL DEFAULT 0,
  updated_at         timestamptz NOT NULL DEFAULT now()
);

-- ─── 分類結果（正式カウントの源泉） ─────────────────────────
CREATE TABLE case_sdg_classifications (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  case_id             uuid NOT NULL REFERENCES cases(id) UNIQUE,  -- 1案件1行（最新のみ保持）
  goal_ids            integer[] NOT NULL,   -- 該当ゴール（複数可）
  indicator_ids       text[] NOT NULL,      -- 該当GI（Top5まで・スコア0.5未満除外）
  confidence_scores   jsonb,                -- {"1.3.1": 0.82, ...}
  ai_reasoning        jsonb,
  is_manual_review    boolean NOT NULL DEFAULT false,
  supporter_confirmed boolean NOT NULL DEFAULT false,
  is_effective        boolean NOT NULL DEFAULT false,  -- RESOLVED確定でtrue（カウント対象フラグ）
  classified_at       timestamptz NOT NULL DEFAULT now(),
  confirmed_at        timestamptz
);

-- 集計用インデックス（配列のunnest集計・案件規模なら十分高速）
CREATE INDEX idx_csc_goal_ids ON case_sdg_classifications USING GIN (goal_ids);
CREATE INDEX idx_csc_indicator_ids ON case_sdg_classifications USING GIN (indicator_ids);
CREATE INDEX idx_csc_effective ON case_sdg_classifications (is_effective) WHERE is_effective;

-- バリアント別の利用設定（§3.4どおり・variants導入後に有効化）
-- CREATE TABLE variant_indicator_settings ( ... );  -- variant Phase 2 と同梱

-- 全テーブル ENABLE ROW LEVEL SECURITY（service_role経由APIのみ）
```

設計判断:
- **`is_effective` フラグを追加**（AGENTS.mdドラフトへの追加提案）。
  「SOS承認 or 自動解決 → 有効化 / SOS拒否 → 破棄 / CLOSED → 対象外」の状態遷移を
  1フラグで表現し、集計クエリは常に `WHERE is_effective` だけで済む。
- `labels` は jsonb（当面 `{"ja": ...}` のみ。多言語化してもmigration不要）。
- `definition_ja` は日本語のみ。**外国語案件はPhase 2の日本語訳
  （description_free_ja / translated_content）を分類入力に使う**ため、定義文の多言語整備は不要。
- ゴールのラベル・色はDBに持たない（既に `messages/*/sdgs.json` に6言語、色は `SDG_COLORS`）。

## 2. カウント規則（AGENTS.md確定分の実装仕様）

```
ゴール別件数   = SELECT goal, COUNT(*) FROM (unnest(goal_ids)) WHERE is_effective
                 → 同一案件・同一ゴールは goal_ids 内で重複しないため自然に「ゴール1件」
ターゲット別   = indicator_ids から導出（indicator '1.3.1' → target '1.3'）。
                 同一案件が同一ターゲットの複数GIに該当 → ターゲットレベルでは1件（DISTINCT case）
GI別件数       = unnest(indicator_ids) の件数
案件一覧       = indicator_ids @> ARRAY[:id] の案件（最深部のみ 自動完了/ユーザー評価あり を区別表示）
合計の注釈     = 全レベルで「※1つの相談が複数の項目に貢献する場合があります」を必ず表示
```

- 集計はオンザフライ（GINインデックス＋案件数規模なら十分）。
  将来遅くなったら夜間バッチで `sdg_goal_counts` キャッシュテーブルに移行（APIの形は不変）。

## 3. API設計

すべて service_role 経由・`requireActiveAppUser()`。スコープは2種:
**admin=全件 / supporter=自団体が関与（ACCEPTED）した案件のみ**。

| エンドポイント | 返すもの |
|---|---|
| `GET /api/impact/summary` | 17ゴール分の `{goal, count}` + 総案件数（注釈計算用）。**L1画面はこれ1本で完結** |
| `GET /api/impact/goals/[goalId]` | 配下ターゲットの `{target_id, label, count}` |
| `GET /api/impact/targets/[targetId]` | 配下GIの `{indicator_id, label, count}` |
| `GET /api/impact/indicators/[indicatorId]/cases` | 該当案件の一覧（タイトル=ja正本・解決日・自動完了/評価ありの別） |

- クエリパラメータ `scope=admin|mine`（roleで強制）。将来 `variant=` を追加（横断=無指定）。
- 暫定版（§6）は summary のみ `source=interim` で先行提供できる。

## 4. UI/UX設計（17を入口とする段階的開示）

### L1: 17ゴールタイル（デフォルト・これだけで完結する画面）

```
┌─────────────────────────────────────────────┐
│ 解決した相談 128件 が貢献したSDGsゴール         │
│ ※1つの相談が複数のゴールに貢献する場合があります │
├────┬────┬────┬────┬────┬────┐
│ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │  ← 公式カラー・ゴール番号・
│貧困 │飢餓 │健康 │教育 │ジェ │水  │     短縮名（sdgs.goalShort）
│ 24 │ 18 │ 41 │ 12 │  7 │  3 │  ← 件数（0件はグレーアウト）
├────┼────┼────┼────┼────┼────┤
│ …17まで。タイルタップ/クリックで L2 へ          │
└─────────────────────────────────────────────┘
```

- 件数降順ではなく**ゴール番号順**（SDGsホイールとしての一覧性・毎回同じ位置）。
- 0件ゴールも薄色で表示（「全17ゴールを見ている」体験を崩さない）。
- ライトユーザーはここで終了。**L1に詳細情報を混ぜない**。

### L2〜L4: ドリルダウン（興味がある人だけ）

```
L1 タイル選択
 └ L2: ゴールNのターゲット一覧（該当のあるものを上に、0件は折りたたみ「すべて表示」）
     └ L3: ターゲット配下のGI一覧（個人向けラベルで表示・件数付き）
         └ L4: 案件一覧（🤖自動完了 / 🌟ユーザー評価あり の区別は最深部のみ）
```

- パンくず: `SDGs > ゴール3 すべての人に健康と福祉を > 3.8 > GI一覧`。
- 各レベルの合計は上位と一致しない（複数ヒット）→ **全レベルに注釈を常設**。
- ターゲット・GIの件数バーは同レベル内の相対値（最大値=100%）で表示し、比較を直感的に。

## 5. 分類フロー（機能4・データを生む側）— 2026-08-19 改訂

**大原則（個人情報保護）: チャット履歴はAIに渡さない。**
支援中のやり取りには氏名・住所・連絡先・健康状態など相談文より濃い個人情報が含まれ、
機械的なマスキングには必ず漏れが出るため。分類入力は
**「最初の案件内容（相談文）」と「最後のサポーター記述（解決後の詳細記入）」に限定**し、
双方ある場合は**後者を重み付けで優先**する（実際に行われた支援の方が解像度が高い）。

```
(1) SOS 案件登録
      ↓ 投稿時AI提案 ai_sdg_suggestion.sdgs_goals（既存）
(2) マッチング成立・チャットで支援（このやり取りは分類に一切使わない）
(3) サポーター「解決済みにする」
      ↓ モーダル: AI提案ゴールを初期値選択済みで提示、確認・修正のみ（最低1・最大3）
        ※記述入力はここでは求めない（SOS拒否→再申請時の「また書くのか」を避ける）
        ※AI提案と人間確定のズレは記録（教師データが育つ + 無修正採用率ログ）
(4) SOS承認（承認と同時に感謝のバッジを送付）→ RESOLVED確定（真クローズ）
      ・SOSが14日放置 → 自動RESOLVED + システムがデフォルトバッジを付与
      ・SOS拒否 → MATCHEDに戻る（ゴール選択は保持し再申請時に再利用）
      ↓ RESOLVED確定を契機にAI②実行: 相談文 + 確定ゴール（+教師データ）→ 指標判定
        （外国語案件は日本語訳側を使う。case_sdg_classifications へ保存・is_effective=true。
         この時点で全解決案件が必ずカウントに乗る）
(5) クローズ後、サポーターへ詳細記入を依頼（努力目標・クローズ後14日でフォーム閉鎖）
      ・確定ゴールの文脈に応じた支援内容の選択式（送信時必須=MUST）
        + 自由記述（任意=WANT・個人情報を書かない前提の欄）
      ・SOSへの一言メッセージ欄（記入の動機づけの中核。支援をやり切った人は挨拶を送りたい）
        → 一回限り・返信不可のシステムメッセージとして配送（終了案件の409ブロックは維持し、
          この特別経路のみ許可）
      ↓ 記入が届いたらその案件のみAI②を再実行し分類を上書き
        （相談文 + 詳細記述、後者を重み優先。1案件1行UNIQUEのまま）
```

- 判定規則（2026-07-12 確定・不変）: サポーター選択ゴールは**重み付け**であり探索範囲の檻ではない。
  AIが枠外ゴールの指標に強い確信を持つ場合は採用可（枠外採用は印を付けて追跡可能にする）。
  複数指標への該当を許容（Top5・スコア0.5未満除外）。どの指標にも落ちない場合は
  indicator_ids 空のままゴールレベルにのみカウント。
- `goal_ids` は「サポーター確定ゴール ∪ 採用指標の属するゴール」。枠外指標を採用しても
  L1タイルとドリルダウンの件数整合が保たれる。
- **分類はRESOLVED確定後に実行**するため、SOS拒否時の分類破棄は発生しない
  （旧設計の is_effective=false 期間は不要になった。フラグ自体は「CLOSED=対象外」の表現として存続）。
- 解決時のAI①（ゴール再分類）は廃止し、投稿時提案を初期値に使う（AI呼び出しは②のみ。
  必要になれば復活可）。コスト試算: 全指標の定義文を注入しても1案件1円未満（Flash系）のため、
  コストを理由とした探索範囲の絞り込みは行わない。教師データが増えたら §6.5 の類似例選抜で注入量を抑える。
- ステップ(5)の記述は教師データの `outcome` 列（§6.5）として蓄積される（旧「一言欄」の後継。
  運用しながら教師データが育つ仕掛け）。記入が無い案件は相談文+確定ゴールの初回分類のまま確定。
- **無修正採用率をログする**: AI提案ゴールをそのまま採用した率を記録し、選択UIの形骸化を数値で監視。
- 最終指標の人間確認ステップは初期リリースでは挟まない（2026-07-12 ユーザー判断）。
  誤分類は運用の中で発見 → AIと壁打ち → 教師データ更新のループで改善する。
- gemini呼び出しは classifySDGs / translateText と同じパターン（`src/lib/gemini.ts` に追加）。
- 夜間バッチ: 分類エラーの再処理（`/api/cron/retry-translations` と同型でOK）。

### 5.1 放置タイマー（2026-08-19 確定）

| 状況 | 挙動 |
|---|---|
| MATCHEDのまま無活動（解決報告なし） | 最終メッセージ（無ければ案件更新日時）から**30日**で自動CLOSED（14日から変更・cron `auto-close-cases` 処理2・実装済み）。解決ではないため分類・カウント対象外 |
| 解決報告後にSOSが放置 | **14日**で自動RESOLVED（既存どおり・cron処理1）+ デフォルトバッジ付与。以後は手動承認と同じくステップ(5)へ。**(5)のトリガーは「SOSの承認操作」ではなくRESOLVED遷移**（手動・自動の両方を拾う） |
| クローズ後にサポーターが記入せず放置 | クローズ後**14日**で記入フォーム閉鎖。分類は相談文+確定ゴールの初回結果のまま確定 |

### 5.2 個人情報を書かせないための注意喚起（2026-08-19 追記）

ステップ(5)の自由記述はAI②に渡り、教師データ `outcome`（§6.5）としても蓄積されるため、
入力段階で個人情報を排除する（後からのマスキングに頼らない = §5大原則と同じ思想）。

- **欄の直上に常時表示**: 「この内容はSDGs分類のためAIで処理され、支援記録として蓄積されます。
  氏名・住所・電話番号などの個人情報は書かないでください」
- **placeholderで見本を見せる**: 例「電力会社との分納交渉に同行し、緊急食料支援につないだ」
  （個人が特定されない書き方の手本。禁止よりも見本の方が行動を変える）
- **送信はブロックしない**（努力目標の思想と一貫）。ただし電話番号・メールアドレス等の
  単純パターンを検知したら非ブロックの確認を出す（「個人情報が含まれていませんか？」→そのまま送信可）
- SOSへの一言メッセージ欄は**分類・蓄積に使わない**（相手本人に届くだけ）ため注意喚起の対象外。
  代わりに「このメッセージは相手にのみ届きます」と明記し、記録用の欄との違いを見せる
- サポーターUIは日本語のみ（i18nスコープ外）のため文言はjaのみで良い

## 6.5 教師データの活用設計（2026-07-06 追記・運営が作成中）

運営側で**教師データ（相談例 → 該当ゴール/GI のラベル付きペア）を作成中**。
分類（振り分け）はこの教師データを参考にする方式を主軸に据える。

### 使い方（3段階・データ量に応じて）

| 量 | 方式 | 内容 |
|---|---|---|
| 〜50件 | **few-shot注入** | AI①②のプロンプトに教師データを例示として直接埋め込む。実装が最も簡単で、当日から効く |
| 〜数百件 | **類似例選抜** | 相談文と類似する教師例をゴール別に数件選んでプロンプトに注入（全件は入れない）。精度と消費トークンのバランスが良い |
| 全期間 | **評価セット** | 教師データの2割を評価用に取り分け、分類器の精度（ゴール一致率・GI Top5ヒット率）を継続測定。プロンプト改善の効果を数値で確認できるようにする |

- 教師データは **GI定義文（§7）の相互検証にも使う**: 「この例がこのGIに落ちるか」を
  定義文でチェックし、落ちなければ定義文側を直す。定義文と教師データは補完関係。
- 教師データが十分に揃えば、GI定義文の網羅性への依存が下がる
  （§7のブロッカーが緩和される — 定義文は「境界の言語化」、教師データは「実例の重心」）。

### 推奨フォーマット（この形で作成いただけると、そのまま取り込めます）

スプレッドシート or JSONL。1行=1例:

| 列 | 必須 | 内容 | 例 |
|---|---|---|---|
| `text` | ○ | 相談文（実案件を使う場合は**匿名化**: 氏名・地名・団体名を除去） | 「電気が止められ、子どもと真っ暗な部屋で過ごしています…」 |
| `goals` | ○ | 該当ゴール番号（複数可・カンマ区切り） | `1,7` |
| `indicators` | 任意 | 該当GI（公式ID・複数可）。**ゴールだけでも十分価値がある** | `1.4.1` |
| `outcome` | 推奨 | どう解決したか一言（分類の文脈になる） | 「電力会社と分納交渉+緊急食料支援」 |
| `note` | 任意 | 判断に迷った点・境界メモ（レビューとプロンプト改善の材料） | 「7エネルギーと迷ったが生活困窮を主とした」 |

作成のヒント:
- **量より分布**: 1ゴールに偏らず、頻出ゴール（1,3,4,8,10,16）に各10例前後あると効き始める
- **境界例が最も価値が高い**: 「AとBで迷う」例に正解と理由（note）が付いていると精度が上がる
- 「該当なし（分類不能）」の例も数件あると、無理な分類の抑制に効く

### 格納と反映

- 確定データは `src/data/sdgs/training_examples.json`（案）にバージョン管理で格納
- 分類APIは実行時にゴール別へ選抜してプロンプトに注入（DBには置かない=カタログと同じ思想）
- 追加・修正はファイル更新のみ（migration不要）

## 7. GI定義文の整備プラン（教師データの補完・優先度は下がる）

対象規模: 17ゴール × 20〜40件 ≒ **300〜500件**の個人向け定義文（日本語のみ）。

提案ワークフロー（AI下書き＋人間レビュー）:
```
1. 公式指標リスト（総務省仮訳）から指標ID・原文を整理（機械的）
2. Geminiで「個人の相談文脈向け」定義文を一括下書き
   例) 1.3.1 原文「社会保護制度によってカバーされる人口の割合…」
       → 個人向け「生活保護・年金・手当などの公的支援制度につながった、
          または利用できるようになった」
3. 運営（SDGs×現場知識）がレビュー・修正 ← ここだけ人間必須
4. seed（src/data/sdgs/indicators_seed.json）に確定版を投入
```
- 下書きは1〜2日で全件生成可能。レビューの体制・所要が実質の律速。
- **全指標を一度に揃える必要はない**: 相談が実際に発生しやすいゴール
  （1貧困・3健康・4教育・8労働・10不平等・16平和あたり）から優先整備し、
  未整備ゴールはAI②をスキップして「ゴールのみ分類」で運用開始できる
  （ゴールレベルのカウントは全ゴールで最初から機能する）。

## 9. 決定事項ログ（2026-07-12 壁打ちで確定）

| 論点 | 決定 |
|---|---|
| サポーターのゴール選択の意味 | フィルタ（檻）ではなく**重み付け**。AIは全指標を探索し、曖昧なときは選択ゴール側に倒す |
| コスト前提 | 全指標の定義文注入でも1案件1円未満 → コストを理由とした絞り込みは不要（§6.5類似例選抜で更に低減） |
| 指標に落ちない案件 | サポーター選択ゴールで**ゴールレベルにのみカウント**（indicator_ids空）。該当なしは該当なしで許容 |
| 解決時モーダル | AI提案ゴールを初期値選択済み+「どう解決したか一言」欄。一言は教師データ `outcome` として蓄積 |
| 品質改善ループ | 最終指標の人間確認は初期は挟まない。誤分類→AI壁打ち→教師データ更新で改善。無修正採用率をログ |

- 捨てた案: 選択3ゴールをAI探索の檻にする（コスト前提が数字で崩れた）/ 指標に落ちない案件を完全に該当なし扱い。
- 残る前提: 教師データの量と分布（受領待ち）/ 一言欄の実記入率 / Step 0 先行の是非（§8-3）。

## 10. 決定事項ログ（2026-08-19 壁打ちで確定 — 個人情報保護と解決フロー）

| 論点 | 決定 |
|---|---|
| チャット履歴のAI入力 | **渡さない**。氏名・住所・健康状態など相談文より濃い個人情報が含まれ、マスキングには必ず漏れが出る。解像度は解決後のサポーター記述で代替する |
| 分類入力と優先度 | 相談文（登録時）+ サポーター最終記述（解決後）。**双方ある場合は後者を重みとして優先** |
| 解決報告時(3)の入力 | ゴール選択のみ（AI提案を初期値・確認修正・最低1最大3）。記述はクローズ後(5)に分離（SOS拒否→書き直し負担の回避）。サポーターがGI 234個に触れることはない |
| 詳細記入(5)の位置づけ | **努力目標**。MUST化も未記入ペナルティもしない。SOSへの一言メッセージ欄を動機づけの中核に置く（送信には選択式の入力が必要） |
| バッジ | SOS承認時に送られる「感謝」。自動RESOLVED時はシステムがデフォルトバッジを付与。**記入の報酬・罰には使わない**。解決カウント（実績）は記入と無関係に常に計上 |
| 状態遷移 | **変更しない**。クローズはSOS承認（または自動）で確定。詳細記入はクローズ済み案件への一回限りの添付（409ブロック維持・特別経路のみ） |
| 放置タイマー | MATCHED無活動の自動CLOSED: 14日→**30日**（実装済み）/ 解決報告後の自動RESOLVED: **14日**維持+デフォルトバッジ / 記入フォーム: クローズ後**14日**で閉鎖 |
| 分類実行タイミング | RESOLVED確定時に即分類（全解決案件がカウント保証）。詳細記入の到着時に該当案件のみ再分類・上書き |
| 自由記述の個人情報対策 | 欄の直上に注意喚起+書き方見本のplaceholder（§5.2）。送信はブロックせず、電話番号等の単純検知で非ブロック確認のみ |

- 捨てた案: 生チャットのマスキング送信（漏れリスク）/ AIによるチャットからの下書き自動生成（チャットをAIに渡す問題が復活）/ 詳細記入のMUST化・バッジの記入報酬化・カウント没収（ペナルティは相互扶助の空気に合わない）/ クローズを記入完了に紐づける（閉じない案件が生まれ、状態遷移が複雑化。getCaseDisplayStatus考慮漏れの前科あり）
- 残る前提: 詳細記入の実記入率（低くても設計は崩れないが精度向上幅が決まる）/ 支援内容タグの語彙設計（§8-7）/ バッジUI（§8-8）
