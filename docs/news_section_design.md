## 1. 一言でいうと

運営が管理画面から書いてトップに並ぶ「お知らせ」欄。読み物に育ち、AIが下書きを手伝う。

---

## 2. 背景: 誰の、何のため

- **主目的は運営の掲示板**。「11月から少人数運営に切り替える」宣言、メンテナンス予定、受付終了(熊本SOSのような)を、サイトの表で伝える場所が今はない。
- **その延長で「このサイトは動いている」を見せ、興味を持って滞在してもらう**。今の読み物は `/story`(創業者の話)だけで、その先がない。お知らせ欄は読み物が増えていく入口になる。
- **団体紹介とインタビューは同じもの**。NPOインタビュー作戦(登録させず「呼べる支援者の電話帳」を作る)で取材した団体を「XXXが参加しました」として紹介し、それが読み物になる。note に載せた長文インタビューは外部リンクで並べる。
- **オーナーは文章を書くのが得意ではない**。管理画面の中に、材料から下書きを作る AI を置く。

11月以降は「休止」ではなく「リソースを減らして細く運営する」。最初の投稿はその宣言文になる(§6.2 にたたき台)。

## 3. 仕様(小さい版)

### 3.1 DB: `news_posts` テーブル 1 つ

既存データに触らない独立テーブル。migration は `migrations/add_news_posts.sql`(ドラフト)。

```sql
CREATE TABLE IF NOT EXISTS news_posts (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    category      text NOT NULL
                  CHECK (category IN ('NOTICE', 'MAINTENANCE', 'SUPPORTER_JOINED', 'INTERVIEW')),
    title         text NOT NULL,
    body          text NOT NULL DEFAULT '',   -- プレーンテキスト(§3.4 の 3 規則のみ)
    external_url  text,                       -- あればトップ・一覧から直接外へ(note など)
    status        text NOT NULL DEFAULT 'DRAFT' CHECK (status IN ('DRAFT', 'PUBLISHED')),
    published_at  timestamptz,                -- 表示日・並び順。公開時に未設定なら now()
    created_by    uuid REFERENCES users(id) ON DELETE SET NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now()
);

-- RLS 有効・ポリシーなし = anon/authenticated は読めない。service_role(API)だけが触る
ALTER TABLE news_posts ENABLE ROW LEVEL SECURITY;

CREATE INDEX IF NOT EXISTS idx_news_posts_published
    ON news_posts (published_at DESC) WHERE status = 'PUBLISHED';

-- updated_at 自動更新(inquiries と同じ形)
CREATE OR REPLACE FUNCTION update_news_posts_updated_at() RETURNS TRIGGER AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;
DROP TRIGGER IF EXISTS set_news_posts_updated_at ON news_posts;
CREATE TRIGGER set_news_posts_updated_at BEFORE UPDATE ON news_posts
    FOR EACH ROW EXECUTE FUNCTION update_news_posts_updated_at();
```

rollback: `DROP TABLE news_posts;`(他テーブルから参照されない)。

種別は 4 つで固定。ラベルと表示色はコード側の定数(`src/lib/constants/news.ts`)に置き、DB には英字コードだけ入れる。

| コード | ラベル | 用途 |
|---|---|---|
| `NOTICE` | お知らせ | 運営体制、受付終了、その他の告知 |
| `MAINTENANCE` | メンテナンス | 事前告知(当日の遮断は従来どおり `MAINTENANCE_MODE`) |
| `SUPPORTER_JOINED` | 参加団体 | 「XXX が参加しました」+ 団体紹介 |
| `INTERVIEW` | インタビュー | note 記事への導入文 + 外部リンク |

### 3.2 管理画面: `/admin/news`

管理ダッシュボード(`admin/dashboard/page.tsx`、1,046 行)には足さず、`/admin/regions` と同じ型の独立ページにする。ダッシュボードのヘッダーにリンクを 1 つ追加。

- 一覧: 状態・種別・タイトル・公開日。下書きと公開中を分けて表示
- フォーム: 種別 / タイトル / 本文 / 外部URL / 公開日 / 状態(下書き・公開)
- AI 下書き(§4): フォーム上部に「材料」欄と「下書きを作る」ボタン。結果はタイトル・本文欄に入る(本文が空でないときは上書き確認)
- 削除は物理削除(公開中の削除は確認ダイアログ)

### 3.3 API

| エンドポイント | 認可 | 内容 |
|---|---|---|
| `GET /api/public/news?limit=3` | 不要 | 公開中の新しい順。返すのは `id, category, title, external_url, published_at` のみ |
| `GET /api/admin/news` | ADMIN | 全件(下書き含む) |
| `POST /api/admin/news` | ADMIN | 新規作成 |
| `PATCH /api/admin/news/[id]` | ADMIN | 更新・公開/下書き切替 |
| `DELETE /api/admin/news/[id]` | ADMIN | 削除 |
| `POST /api/admin/news/draft` | ADMIN | AI 下書き生成(§4)。DB には書かない |

- 認可は `requireActiveAppUser(request, { roles: ['ADMIN'] })` を使う(`src/lib/api/auth.ts`)。
- 入力検証: `title` ≤ 120 文字、`body` ≤ 20,000 文字、`external_url` は `http(s)://` のみ(`validation.ts` に `isHttpUrl` を追加)、`id` は `isUuid`。
- 公開・下書き戻し・削除は `audit_logs` に記録(`news_post_published` / `news_post_unpublished` / `news_post_deleted`)。既存テーブルで追加なし。
- 公開 API は `Cache-Control: no-store`(featured-supporters と同じ)。当初 `s-maxage=60, stale-while-revalidate=600` にしたが、公開直後にトップを確認すると CDN が公開前の空応答を最大 10 分返し続けた(2026-09-17 プレビューで実測)ため撤回。

### 3.4 公開側

- **トップページ**: ヒーロー直下(現在の実績ストリップの上)に「お知らせ」ブロック。新しい 3 件を「日付・種別チップ・タイトル」の 1 行で並べ、末尾に「すべて見る → /news」。**公開中が 0 件、または取得失敗のときはブロックごと出さない**(空の欄を見せない)。既存の `featured-supporters` と同じく `useEffect` で公開 API を fetch する。
- **`/news`**: 公開中の全件を新しい順に、公開日(日本時間)の年ごとに「2026年」の見出しでまとめる(2026-09-17 ユーザー要望)。並び順はトップと同じく公開日の降順 → 同じ日は登録が新しい順(公開日は日単位なので同日は同点になる。2026-09-17 プレビューで確認)。
- **`/news/[id]`**: 記事本文。`privacy` / `terms` と同じサーバーコンポーネントで描き、`generateMetadata` でタイトルを `<title>` と OGP に出す(団体紹介を SNS で共有したとき記事名が出るため)。データはサーバーで `supabaseAdmin` から直接読む(公開 API は経由しない)。下書き・存在しない id は 404。
- **リンク先の規則**: トップ・一覧からは **必ずサイト内の `/news/[id]`** に入る(2026-09-17 変更。当初は外部リンクがあれば直接外へ飛ばす設計だったが、困っている人がクリックした瞬間に見知らぬサイトへ飛ぶのは怖い、という判断)。`external_url` は記事ページの本文の下に OGP カード+「続きを読む(外部サイトが開きます)」ボタン+リンク先ドメインとして出す(新規タブ、`rel="noopener noreferrer"`)。
- **本文の書式**: プレーンテキスト。規則は 4 つだけ。
  1. 空行で段落を分ける
  2. 行頭の `## ` は小見出し
  3. 文中の `http(s)://` で始まる文字列は自動でリンク(URL は ASCII のみ。直後に日本語が続いても巻き込まない)
  4. **URL を 1 行だけで置くと、リンク先の OGP(画像・タイトル・説明・ドメイン)をカードで表示**(2026-09-17 ユーザー要望。サーバーで取得し 24 時間キャッシュ、4 秒で諦めてドメインだけのカードに。内部アドレスは拒否)。外部リンクボタンの上にも同じカードを出す
  描画は React 要素で組む(`dangerouslySetInnerHTML` は使わない)。ライブラリは入れない。

### 3.5 言語

- 本文・タイトルは **日本語のみ**。`en` / `zh` のトップにも同じ日本語の見出しを出す(「動いている証拠」を隠さない)。
- UI 文言(欄の見出し「お知らせ」「すべて見る」、種別ラベル 4 つ、記事ページの「一覧へ戻る」など十数キー)は `messages/*/landing.json` に `news` 名前空間を足し、**6 言語のキー数を揃える**(現在 763 キー)。
- `/news` `/news/[id]` は `/story` と同じ `JaOnlyNotice` を上に出す。

## 4. AI 下書き

### 4.1 入口(フォームの「材料」欄)

| 種別 | 材料欄 | 出力 |
|---|---|---|
| 参加団体 | **2 欄**: ①団体のサイトから写した文 ②電話などで聞いたメモ | タイトル + 本文(400〜600 字、小見出し 2〜3) |
| インタビュー | **1 欄**: note 記事の URL とタイトル、要旨や印象に残った話 | タイトル + 導入文(100〜200 字)。`external_url` に note の URL を入れるのはオーナー |
| お知らせ | **1 欄**: 伝えたいことの箇条書き | タイトル + 本文(300 字前後) |
| メンテナンス | **1 欄**: 日時・所要時間・影響する機能 | タイトル + 本文(150〜250 字)。構造プロンプトはほぼ定型文 |

URL を貼ると自動でサイトを読みに行く機能は **作らない**(サーバーから任意 URL を取得する仕組みは取得失敗・JS 描画・安全面の負担が大きい)。必要な部分をオーナーがコピペする。

### 4.2 プロンプトは 2 層

**声(全種別共通)** — サービスの思想(`AGENTS.md`)をそのまま文章の規範にする。

- 読者は「困っている人」と「支援する団体」の両方。困っている人を怖がらせない言い回しを選ぶ
- SDGs の番号・用語を前面に出さない(SDGs はサービスの言語であって、相談者の言語ではない)
- 「管理者」ではなく「運営」と呼ぶ。「明日もsamasama」の表記を崩さない
- です・ます調。1 段落 3 文まで。見出しは体言止め
- 誇張・断定を避ける。「必ず解決」「すぐに」等は書かない

**構造(種別ごと)** — 書く順番と分量だけを指定する。

- 参加団体: 団体名と種別(NPO/行政/企業) → 活動地域 → 何をしている団体か → どんな困りごとに応えられるか → 団体からのひとこと(材料にあれば)
- インタビュー: 誰に何を聞いたか → 印象に残った一言 → 「続きは note で」
- お知らせ: 何が・いつから → **変わらないこと** → 変わること → 問い合わせ先(`/contact`)
- メンテナンス: 日時(JST) → 所要時間 → 影響する機能(ログイン・相談投稿・メッセージ) → お詫び → 完了後の案内

### 4.3 鉄則(プロンプトに必ず入れる)

1. **材料にない事実を書かない**。活動内容・実績・地域を推測で盛らない。足りない所は `[要確認: 活動地域]` の形で本文に残し、オーナーが埋める
2. **個人名・電話番号・メールアドレスは、材料に「掲載可」と明記がない限り本文に出さない**(電話メモには担当者の連絡先や「ここは書かないで」が混ざる)
3. 相談者個人の事例・相談内容は書かない(材料に混ざっていても捨てる)
4. 出力は JSON `{ "title": string, "body": string }` のみ。本文は §3.4 の 3 規則で書く

### 4.4 実装

- `src/lib/newsDraft.ts` を新設(`disasterNeeds.ts` と同じく `gemini.ts` から独立)。モデルは既存と同じ `gemini-2.5-flash`。
- `gemini-2.5-flash` は思考トークンが `maxOutputTokens` を内側から消費する(`gemini.ts` の注記)。本文 600 字 + 思考分を見て `maxOutputTokens` は 4,096 程度に取る。
- 材料は各欄 8,000 文字まで。API キー未設定時は 503 を返し、フォームに「AI 下書きは使えません(手で書けます)」と出す(既存のデモモードのような偽の下書きは返さない)。
- **品質は実装前に確かめる**(§8 前提 1)。伊藤さんの取材材料(`docs/articles/`)を「参加団体」の 2 欄に見立てて 1 回流し、オーナーの手直しで済む文が出るかを見る。

### 4.5 note 記事ワークフロー(INTERVIEW 用、2026-09-19 追加)

インタビューの取材メモから、note に貼る長文記事を管理画面で起こす。2026-09-08 の伊藤さん記事(`docs/articles/`)を私(Claude)が手作業で作った手順を、オーナーが一人で回せるようにしたもの。材料はテキストのみ(録音の文字起こしは対象外、2026-09-19 ユーザー判断)。

**工程は 3 つ + 貼り付け**(`/admin/news` で種別「インタビュー」を選ぶと出るパネル):

1. **切り口を 3 案**: 取材メモを読んだ AI が「タイトル案 / 誰に何を伝えるか / 冒頭の一文 / 理由」を、互いに軸の違う 3 案で出す。オーナーが 1 つ選ぶ(「どの話を推すか」は本人にしか決められないので、この工程は人の手に残す)
2. **本文**: 選んだ切り口で記事を書く(目安 3,000〜4,000 字。材料が少なければ無理に伸ばさない)。同時にサイト用の導入文(100〜200 字)も書き、投稿のタイトル・本文が空なら埋める
3. **見直し**: 別の目(ファクト / 倫理・個人情報 / 編集)で本文を読み、**取材相手に確認・了承をもらう項目**と**ライターが直す箇所**をリストにする(伊藤さん記事の「第 3 部 掲載前チェックリスト」に相当)。オーナーが直して取材相手に送り、OK をもらってから note に公開
4. **貼り付け**: 「note 用にコピー(書式付き)」で HTML(h2 / h3 / blockquote / p)と文章をクリップボードへ。note の本文欄に貼って見出し・引用が残るかは**実機で要確認**(残らなければ「文章だけコピー」で貼って見出しを手で付ける運用)。公開後、note の URL を外部リンク欄に入れて投稿を公開する

**ライターの人格**(`src/lib/news/articlePrompt.ts`): 人物の物語で運ぶ(原点・転換点・いま大切にしていること)/ 当事者の尊厳を損なわない・感動の押し売りをしない / 読者は 3 人(困りごとを抱えて相談できていない人・受け入れ側になりうる経営者や団体・一般読者)で、①を怖がらせない順序で書く / 引用は材料にある言葉だけ / SDGs を前面に出さない。鉄則は §4.3 と同じ+「取材相手が語った支援先の人のエピソードは特定されない粒度でのみ使う」。

**保存**: `news_posts` に `interview_source`(取材メモ)/ `note_angle`(選んだ切り口 jsonb)/ `note_article`(本文)/ `note_checklist`(確認リスト)の 4 列。投稿と一緒に「保存」で保存する(生成 API `POST /api/admin/news/article` は DB に書かない)。取材メモを DB に持つのは、日を改めて切り口を変えて書き直せるようにするため。オフレコは「非公開」と付ければ AI は使わないが、DB には残るので、載せたくない話はメモから消してから貼る。

**モデル**: `gemini-2.5-flash`(`gemini-2.5-pro` はこの API キーでは 404、2026-09-19 実測)。所要時間の実測: 切り口 14 秒 / 本文 20〜25 秒 / 見直し 20 秒。maxOutputTokens は本文 16,384、他 8,192。

**実測(2026-09-19、伊藤さんの取材内容を模したメモ 1,200 字)**: 切り口 3 案は軸が異なる(転換点 / 8 年の伴走 / 愛情と想像力)。本文は 2,500 字で電話番号・オフレコ・前職を除外、`> ` 引用 5 箇所。見直しは「14 年間たった一人で」の誇張、「取材を終えて」が取材相手の SDGs への正直な距離感と食い違う点、8 年の事例が読者のハードルになる点を指摘した。

## 5. 種別ごとの扱い(温度差)

| 種別 | AI の効き | 補足 |
|---|---|---|
| 参加団体 | **本命**。材料から紹介文を組み立てる価値が最も大きい | 掲載前に団体の確認が要る(§6.1) |
| インタビュー | **大**(§4.5)。取材メモから note 記事本体を起こし、見直しの確認リストまで出す。サイト側は導入文 | note 公開後に `external_url` を入れる。本文は導入文のみ |
| お知らせ | 中。箇条書きを文章にする | 11 月の宣言文は AI に任せず、一度きりの重要文として人が書く(§6.2) |
| メンテナンス | ほぼ穴埋め | 事前告知はここ、当日の遮断は `MAINTENANCE_MODE`(役割は別) |

## 6. 運用ルール

### 6.1 参加団体の記事は、団体の OK をもらってから公開

1. 材料(サイトの文 + 電話メモ)から下書きを作り、オーナーが直す
2. **下書きのまま**、本文をメール等で団体に送って確認してもらう(サイト内のプレビュー共有は作らない。下書きは外から見えない)
3. OK が出たら「公開」に切り替える
4. 修正依頼が来たら本文を直して再確認

note のインタビュー記事(伊藤さんの回で「掲載前に本人確認必須」とした手順)と同じ。

### 6.2 11 月の宣言文(たたき台)

「リソースを減らす」は、困っている人には「誰も見てくれないかも」と読める。**変わらないことを先に**置く。以下はたたき台で、公開前にオーナーが書き直す前提。

> **タイトル**: 11月からの運営体制について
>
> 明日もsamasama は、2026年11月から、少人数での運営に切り替えます。
>
> ## 変わらないこと
>
> 相談の受付はこれまで通り続けます。投稿いただいた相談は、運営が必ず確認します。
> サポーター団体とのやりとりやメッセージ機能も、そのまま使えます。
> お問い合わせフォームからのご連絡には、運営が返信します。
>
> ## 変わること
>
> 返信や、新しいサポーター団体のご案内に、これまでより時間をいただく場合があります。
> 新しい機能の追加は当面お休みし、安定して使える状態を保つことを優先します。
>
> このお知らせ欄では、参加してくださった団体の紹介や、支援の現場で活動する方へのインタビューを、これからも少しずつ掲載していきます。
>
> 困ったときは、ひとりで抱え込まずに相談を送ってください。

### 6.3 その他

- 公開を取り消したいときは「下書き」に戻す(削除しない)。削除は誤投稿のときだけ
- 相談者個人の事例は書かない(インパクトダッシュボード設計と同じ個人情報方針)
- 種別「メンテナンス」の投稿は、作業が終わったら下書きに戻すか、本文末尾に「完了しました」を追記する

## 7. やらないこと(捨てた枝)

- 写真・ロゴのアップロード(Storage バケットとアップロード UI が要る。写真つきの読み物は note に書いて外部リンク。リンク先の OGP 画像はカードで表示できる)
- 予約投稿、固定表示、手動の並び替え(公開日順のみ)
- 多言語の本文、翻訳
